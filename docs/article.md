# When an Agent's Notes Start Sounding Like the User

An agent was reading another agent's terminal. In the input area it saw a plausible next instruction, phrased like a task the operator might have typed. The text was a suggestion generated by the interface, displayed in gray. No person had submitted it. For a moment, the observing agent treated it as a draft instruction and nearly passed it into the workflow.

Nothing about the sentence itself marked it as dangerous. The error was in its origin. The observer had the words but not the state of the interface that gave those words meaning. A gray suggestion, a submitted human message, a customer message, and an agent's own note can all look like ordinary text once copied into a transcript. If another agent receives only that flattened text, it may assign the wrong authority to it.

The same confusion can build quietly with one person and one agent. An agent writes project notes or memory after a conversation. Weeks later, another session loads those files as context. A sentence such as “the user prefers X” may be the agent's summary, its guess, or a record of the user's exact words. Without a visible source, all three can read like instructions from the user. More agents make the confusion travel faster, but they are not required for it to happen.

We call the record of origin **authority provenance**. For a consequential instruction, the questions are plain: Who said it? When? Was it actually submitted by a human with authority over this work? What action did those words permit? A source reference and a timestamp do not answer the last question by themselves, but they make the first three checkable.

## Why the mix-up went unnoticed

Notes are written to help the next session move quickly. That is exactly why their voice matters. A useful summary arrives beside the current task, often without the conversation that produced it. Repetition makes it seem settled. In our own memory store, we counted 294 files: none used a human-quote marker, 31 described what the user said, wanted, or decided, and a linter flagged 18 unquoted human-decision claims. Those counts do not prove every claim is wrong. They show how much reading depends on trust in an earlier agent's phrasing.

## The same term, a different shape

People often use *agent orchestration* for one human prompt that fans out into a task tree. Agents complete subtasks and exit within minutes or hours; state largely lives inside one run and often one vendor. The work behind these examples had a different shape: roughly 50 agents active at peak across two vendors and a third model, lanes that ran for weeks through rotation and handoff, a supervisor for each client, and coordination between supervisors. The human kept interjecting and approving while actions reached real production systems. Delivery routing, a question queue, a rotation ledger, and quote verification grew from operating that arrangement.

The hard part was organizational. A handoff can drop a task. A relay can change the meaning or time of an approval. A later reader must decide whose words count and who follows up. The operational cost was visible the same night the host thrashed on memory and a new supervisor could not receive handoff notices because its route had not been registered. Those were ordinary system faults alongside the authority problem, and they made continuity matter.

## One agent can reach the same problem

Scale accelerated the failure until it was easy to see. It did not create it. One person working with one agent for months can accumulate the same stack of notes. The agent's own past sentences may then be read as if they were fresh human instructions. That is why this practice is useful outside a large agent fleet: when a memory file attributes a decision to the user, the next session should be able to find the user's words, their time, and the scope of the decision.

## Separate words from judgments

We started by giving human words and agent judgments different visible forms. A human quote is recorded as `𝕌MMDD HH:MM verbatim words⟧`, with the time produced by a tool that reads the original human session. A card pointer uses `𝕌#447⟧`. The quote contains the person's words only; source references sit outside it. Agent interpretations use a bold model letter and a different closing mark, for example `𝗫author MMDD HH:MM interpretation⦘`. Older quote and judgment formats still work.

The distinction matters because a summary can be useful and still be wrong. In one earlier workflow, an agent stored a human's design direction and its own inference about storage layout in the same note. Later agents read the whole note as if it were the approved design. Several machine configurations drifted from the design document. The correction was not to ban summaries. It was to keep the approved text separate from the inference, then make the later reader check which part had authority.

An approved design document can also carry authority within its approved scope. An old agent note cannot silently override it. When a note conflicts with the underlying human instruction, the team needs to correct the note, not promote its wording to a new rule by repetition.

The same separation applies to messages that are not operator approval at all. A customer can supply facts about a problem without authorizing a production change. Tool output can contain a quoted instruction without becoming a new human instruction. A suggestion in an input field is not a submitted message. Treating any of these as approval collapses different roles into one undifferentiated stream of text.

## Relays need accurate metadata

It would be impractical to require the human to repeat the same approval in every worker's terminal. A named supervising agent can relay an approval. The worker should receive the human's exact words and their time, either directly or through a reference to a record that contains both. The permitted action is limited to those words. An approval for one target, recipient, or deployment window does not automatically cover a neighboring one.

A recent relay showed why the time must be checked as carefully as the words. A supervising agent forwarded four human quotes. Their wording was accurate. Their timestamps were not: the supervisor had estimated each time while preparing the relay, and every estimate was later than the actual message by between two and twenty-five minutes.

Another agent noticed that at least one cited time was later than the time the relay itself had been sent. That sequence could not be right. The agent used `provenance verify` to check the quotes against the original session, inspected the source messages, and corrected all four timestamps. The content of the approval did not change. The error was metadata that had been filled in casually during forwarding.

The pattern repeated while we were adding this rule to the tool. A relay about using the skill cited a loose `20:2x` time window. The original human message was at `20:11`. This time the mistake was caught while writing the rule itself. It made the operating rule more specific: agents should generate new citations with `provenance quote`, which reads the source timestamp and prints the quote with its source line. A relayed citation keeps its original time only after verification. Memory rules now require human words to carry that marker and tool-produced time when written or changed; we correct older files as we touch them, rather than claiming a complete historical repair.

There is a useful limit to this check. The verifier allows a small time tolerance so a human-readable citation can still match a source message. A timestamp two minutes late can therefore pass the match. The receipt prints the actual source time, which still has to be compared with the relayed time. A timestamp farther outside the window fails, prompting a source check. In this case, checking the receipt and session together exposed the full set of errors. A green verification result should not be read as a declaration that every character of the citation metadata was exact.

The tool's receipt includes the matched human text, the source time and location, and a hash of the source line. It rejects assistant and tool messages as sources for a human quote. That is useful evidence of occurrence. It does not determine whether the speaker could authorize the action, or whether the requested action stays inside the quote's scope. Those are separate decisions for the workflow and, where required, the human.

Even a log entry labeled `user` is not enough on its own. An agent's delivered message can be written into a receiving agent's session with that label. We now compare candidate messages against an append-only delivery log containing hashes of the final text sent to a pane, and reject known deliveries as human sources. The original human session remains the place to check the quoted words. A tool-use hook makes one narrow automatic check: if those words match a unique human message in the current session but the cited time is wrong, it returns the source time. It stays silent when it cannot establish that match.

## A linter cannot read a person's mind

We also built a linter to find records that claim a human decision without a human quote, and to flag agent interpretation apparently placed inside a human quote. Its first inference rule was too broad. It treated everyday reasoning words, the equivalents of “should” and “so,” as signs that an agent had added its own conclusion. On real decision files, all fourteen inference findings were false positives. The words were part of what the human had actually said. People make guesses, explain reasons, and ask rhetorical questions in their own instructions.

We removed those general words from the heuristic. The current check looks for stronger signs of agent voice, such as another agent's judgment brackets or a statement that refers to the user in the third person. It remains advisory: a person can use third-person language for someone else, and a rule description can look like an uncited approval claim. Reviewing the later findings confirmed both kinds of noise.

The more reliable check uses a source. When a quote has a session or log reference, `lint --verify` can compare the quoted text with a human message there and report when it cannot find it. The linter can then catch a mixed quote because the words no longer match the original, rather than because it guessed the writer's intent from “so.” If no source is attached, a lexical warning is only a prompt to review the record. It is not a verdict.

This is a general lesson for provenance tools: syntax can make a claim inspectable, but syntax alone cannot certify the claim. The system should carry the reference needed to check it. It should also show clearly when no such reference exists.

## Where the workflow stops

Our agents continue ordinary implementation choices within their assigned tasks. They stop for human approval before writing official customer data, setting or performing a production deployment window, changing security access beyond routine permissions for their own component, deleting something already created, or submitting work externally or spending money. A valid relay can carry that approval to a worker, but the relay cannot widen it.

Other incidents have reinforced the boundary. A worker once rejected a valid relayed approval and demanded that the human answer again in its own pane, adding friction without improving the evidence. In another case, an agent tried to answer a permission prompt on the human's behalf; that was stopped. A message was also once addressed by its position on a screen rather than by the recipient's identity. These are different failures, but each loses a part of the chain between a person's instruction and the action taken: the original speaker, the approved scope, or the intended recipient.

The working practice is modest. Keep the human's words distinct from agent analysis. Preserve the source and actual time when forwarding approval. Resolve card and queue pointers to the underlying human response before treating them as evidence. Check the recipient by identity. Use the verifier where a session exists, and read its receipt rather than treating success as a blanket authorization. Leave ambiguous or out-of-scope actions with the supervising agent or human who can resolve them.

As agents handle more operational work, source attribution needs the same care as any other input to a system. A durable record lets the next person or agent inspect the words, source, time, and scope before carrying an instruction forward.
